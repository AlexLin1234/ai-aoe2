# Debug report: window focus edge cases and DPI-scaled coordinates

- **Symptom:** Live control could click and move villagers but misbehaved around window focus, and the planner repeatedly reported it could not read resources, population, or the command panel.
- **Root causes:**
  1. **DPI virtualization (the big one).** The process was DPI-unaware, so `GetWindowRect` returned logical pixels (1536x864) while `mss` captured physical pixels (1920x1080) on this 125%-scaled display. Every frame was the top-left 80% of the game — the resource bar edge, minimap, and command panel were cropped away — and every normalized click resolved against the wrong rect.
  2. **`is_foreground` was exact-handle only.** A modal dialog, popup, or second top-level window of AoE2 counted as "not focused" even though the game owned the keyboard.
  3. **`find()` aborted on one bad window.** An `OpenProcess` failure inside the `EnumWindows` callback killed the whole enumeration, which the loop read as "the game vanished" — its hard kill switch.
  4. **Focus stealing itself.** The bot fought the user for the foreground every cycle, injected a blind Alt tap into whatever app was focused, and made the machine unusable while it ran. Removed entirely — see "User-granted control" below.
  5. **Transient focus loss crashed the run.** `RuntimeError("could not focus AoE2 before screenshot capture")` ended the loop whenever a notification or the user stole focus for a moment.
  6. **Geometry was cached across cycles.** A moved, resized, or just-restored window (a minimized one reports a (-32000, -32000) rect) kept its stale rect; `require_foreground()` now re-reads it each time.
  7. **An unusual configured safety hotkey** raised `KeyError` on the watchdog's first poll, silently disarming the F12 emergency stop.
- **Fix:** Per-monitor-v2 DPI awareness at startup (`utils/dpi.py`); capture and click bounds both switched to the client rect (`TargetWindow.capture_rect`) so the frame the model sees is exactly the space clicks resolve against; foreground check accepts owned/sibling windows of the game's process; per-window failures in enumeration are skipped and matches ranked foreground-then-largest; geometry re-read on every handover; losing the foreground became a skipped cycle instead of a crash.
- **User-granted control (final design).** AoE2 only accepts synthetic input while it is foreground, so the bot needs focus to play — but it must never take it. The focus-stealing code was therefore deleted rather than made conditional: `WindowManager` has no `focus()`, no `SetForegroundWindow`, no `AttachThreadInput`, and no synthetic Alt tap (the Alt tap was the one input the bot could send into another application, to gain foreground rights). What remains is `require_foreground()`. The loop waits, polling at `window.foreground_poll_seconds`, until the user clicks into the game, then hands control straight back the moment they click away — no capture, no planner calls, no input while waiting. `InputDriver.focus_check` re-verifies foreground immediately before every injected event and fails closed when no check is wired, so a mid-batch alt-tab cannot type the rest of a batch into the user's app. `tests/test_window_focus.py` asserts the absence of the activation APIs so the capability cannot quietly return.
- **Evidence:** Live probe showed the rect go from 1536x864 to 1920x1080 and a full-frame capture including the previously-cropped UI; background-to-foreground focus took 250 ms. A one-cycle live run detected the in-game menu, auto-resumed with Esc, and correctly gated actions. A 75-second live run produced 10 consecutive cycles, ~4.2-5.4 s each, with all 40 actions succeeding and zero focus failures; the after-frame showed the menu closed, a villager selected, and villagers commanded. A contention run logged `yielding the desktop to the user` and then `AoE2 is foreground again; resuming control` with no focus fight.
- **Regression tests:** `tests/test_window_focus.py` (client-rect preference, foreground acceptance matrix, absence of the activation APIs, `require_foreground` refusal and geometry refresh, input withheld on focus loss, fail-closed driver, hotkey validation) and `tests/test_loop_handover.py` (handover on foreground, immediate handback, no capture/planning/input while the user is elsewhere, `--once` explaining the handover). 42 tests pass; Ruff clean on all edited files.
- **Status:** DONE — verified against the running game. Pre-existing repo-wide Ruff `I001` import-order findings in untouched files were left alone.
