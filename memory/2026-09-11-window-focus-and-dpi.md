# Debug report: window focus edge cases and DPI-scaled coordinates

- **Symptom:** Live control could click and move villagers but misbehaved around window focus, and the planner repeatedly reported it could not read resources, population, or the command panel.
- **Root causes:**
  1. **DPI virtualization (the big one).** The process was DPI-unaware, so `GetWindowRect` returned logical pixels (1536x864) while `mss` captured physical pixels (1920x1080) on this 125%-scaled display. Every frame was the top-left 80% of the game — the resource bar edge, minimap, and command panel were cropped away — and every normalized click resolved against the wrong rect.
  2. **`is_foreground` was exact-handle only.** A modal dialog, popup, or second top-level window of AoE2 counted as "not focused" even though the game owned the keyboard.
  3. **`find()` aborted on one bad window.** An `OpenProcess` failure inside the `EnumWindows` callback killed the whole enumeration, which the loop read as "the game vanished" — its hard kill switch.
  4. **Focus was fire-and-check-once.** It slept 0.1s after `SetForegroundWindow`; borderless/fullscreen activation is asynchronous and often needed longer. It also injected a blind Alt tap into whatever app was focused, on the first try.
  5. **Transient focus loss crashed the run.** `RuntimeError("could not focus AoE2 before screenshot capture")` ended the loop whenever a notification or the user stole focus for a moment.
  6. **Geometry was read before the restore.** A minimized window reports a (-32000, -32000) rect; focus never re-read it.
  7. **An unusual configured safety hotkey** raised `KeyError` on the watchdog's first poll, silently disarming the F12 emergency stop.
- **Fix:** Per-monitor-v2 DPI awareness at startup (`utils/dpi.py`); capture and click bounds both switched to the client rect (`TargetWindow.capture_rect`) so the frame the model sees is exactly the space clicks resolve against; foreground check accepts owned/sibling windows of the game's process; per-window failures in enumeration are skipped and matches ranked foreground-then-largest; focus polls to a deadline with the Alt tap demoted to a fallback and the foreground lock timeout temporarily cleared; focus returns refreshed geometry; focus failure became a recoverable skipped cycle with backoff.
- **Cooperative focus (requested mid-session):** AoE2 only accepts synthetic input while foreground, so the bot must hold focus to play — but it now never takes focus back from the user. `window.yield_to_user` (default true) means it takes focus once at startup, and afterwards stops acting the moment another window is focused, skipping capture, planning, and input entirely until the game is in front again. `InputDriver.focus_check` re-verifies foreground immediately before every injected event, so a mid-batch alt-tab cannot type the rest of a batch into the user's app.
- **Evidence:** Live probe showed the rect go from 1536x864 to 1920x1080 and a full-frame capture including the previously-cropped UI; background-to-foreground focus took 250 ms. A one-cycle live run detected the in-game menu, auto-resumed with Esc, and correctly gated actions. A 75-second live run produced 10 consecutive cycles, ~4.2-5.4 s each, with all 40 actions succeeding and zero focus failures; the after-frame showed the menu closed, a villager selected, and villagers commanded. A contention run logged `yielding the desktop to the user` and then `AoE2 is foreground again; resuming control` with no focus fight.
- **Regression tests:** `tests/test_window_focus.py` (client-rect preference, foreground acceptance matrix, activation waiting, Alt-as-fallback, input withheld on focus loss, hotkey validation) and `tests/test_loop_focus_recovery.py` (startup focus, yield/resume, no planner spend while yielding, backoff selection, recoverable refusal). 43 tests pass; Ruff clean on all edited files.
- **Status:** DONE — verified against the running game. Pre-existing repo-wide Ruff `I001` import-order findings in untouched files were left alone.
