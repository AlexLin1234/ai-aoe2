# Debug report: the bot kept popping up the pause menu

- **Symptom:** During live runs the in-game pause menu kept appearing, and the agent stopped playing whenever it flickered.
- **Root cause:** Nothing in the capture path can open it — `mss` grabs pixels through a screen DC, sends no input, and the bot has no focus-stealing code. The only Escape the process can send is `_auto_resume`'s `pause_menu_toggle`, and **Escape is a toggle**: pressed while the game is running it *opens* the pause menu. It fired on a single screen classification of a screenshot that was a whole planning round old (measured cycles: 4.2–5.4 s), for a label the model itself confuses — the in-match overlay is titled "Main Menu", so `menu` and `paused` are used interchangeably, and a dark or transitional gameplay frame reads as either. One false positive therefore *created* the overlay; the next cycle read the real menu and Escaped again, and the overlay ping-ponged open and shut. Two more one-way doors ran off the same single frame: `executable_actions` gated all input on `screen == "gameplay"`, so every flicker cost a full recheck delay (up to 5 s), and one `postgame` reading ended the run and spent an end-game review.
- **Fix:**
  1. **Confirm before toggling.** The same overlay must be read on `agent.screen_confirm_cycles` (2) consecutive cycles, and a frame captured immediately before the keystroke must show the world still frozen: `perception/motion.moved_fraction` compares the planner's frame with a fresh one at 96 px wide and refuses the Escape when more than `input.auto_resume_motion_threshold` (0.5%) of it has moved. A pause overlay freezes the world; a running game never is still across seconds.
  2. **One toggle at a time.** At most one Escape per `input.auto_resume_cooldown_seconds` (6 s), the confirmation streak is reset after each send, and after `input.auto_resume_max_attempts` (3) Escapes that did not restore gameplay the loop stands down with a warning instead of fighting the menu. Gameplay returning clears all of it.
  3. **A flicker no longer stops the agent.** Input stays gated while an overlay is genuinely up, but a non-gameplay reading that follows gameplay now rechecks after `agent.flicker_recheck_seconds` (0.4 s) instead of the plan's delay, for up to `agent.flicker_tolerance_cycles` (2) cycles, so a momentary overlay costs one quick cycle rather than seconds. A sustained overlay falls back to the plan's own pace so it cannot burn the call budget. `postgame` now also needs two consecutive readings before the run ends.
- **Telemetry:** every withheld toggle is recorded as an `AUTO_RESUME` result with `sent: false` and the reason (`confirming`, `cooldown`, `the world moved (...)`, `stood down`). Only delivered toggles enter planner history.
- **Regression tests:** `tests/test_motion.py` (frozen world, cursor-only movement below threshold, moving units above it, resized window) and `tests/test_loop_handover.py` (confirmed overlay under either label, no toggle on a single frame, no Escape when the world moved, one toggle per cooldown, stand-down and its reset, fast recheck on a flicker versus backing off on a real overlay, one postgame frame not ending the run).
- **Status:** DONE in code and tests — 54 tests pass, the 3 remaining failures are the pre-existing pywin32-only ones that cannot run off Windows. **Not yet verified against the running game:** the motion threshold is the one number worth re-checking on a real Dark Age frame — if the bot now sits in front of a genuine menu, the telemetry message names the measured motion, and `input.auto_resume_motion_threshold` should be raised to just above it.
